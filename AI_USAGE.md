# AI usage

This project was built with substantial help from OpenAI Codex. Most implementation code was generated by Codex, including the Bun/Hono/SQLite backend, React interface, tests, and Cloudflare adapter. Codex also helped with documentation, browser checks, deployment, and the video. This document records those contributions and the corrections made during development.

## What the candidate directed

The candidate accepted the proposed approach of allocating seats when payment succeeds, with `refund_required` for a successful payment that can no longer secure a seat. They requested a more complete app interface, generated English narration, a public GitHub repository, and deployment to their Cloudflare account. They completed the Wrangler browser login and chose the workers.dev address.

These were product and delivery decisions. The implementation and automated checks were AI-assisted.

## Where AI helped most

Codex turned the last-seat rule into tests against a real SQLite database. The concurrency test starts eight independent processes with separate connections, then releases them together. It checks that exactly one payment gets the last seat and the other seven record a refund obligation.

A separate Codex reviewer examined the backend, concurrency tests, interface, and Cloudflare changes. Playwright exercised the running app, including recovery after a payment response was deliberately dropped. The [verification notes](docs/verification.md) describe what was checked and the limits of that evidence.

## What needed correcting

| Issue found during development | Correction |
| --- | --- |
| An invalid-input test passed an empty array as test arguments, so it sent no body instead of JSON `[]`. | Wrapped each case in `{ body }` so the test exercised the intended input. |
| The explanation of payment replay blurred an old attempt's result with the booking's current status. | Clarified that replay returns the original attempt alongside the current booking. |
| A cached class selector could show three learners while the refreshed roster showed four. | Kept occupancy with the roster response; the selector now shows class capacity. |
| Oversized requests could leave an unfinished body stream when forwarded to the Durable Object. | Buffered the body with an 8 KiB limit before forwarding, then checked fixed-length and chunked requests. |

Agent review and tests identified these corrections; the candidate provided the product direction described above.

## Illustrations and narration

The two class illustrations were generated and saved as WebP images. The walkthrough uses Microsoft Andrew Neural through `edge-tts`, automated browser capture against a separate demo database, and FFmpeg for assembly. The voice is generated, not the candidate speaking. That disclosure appears in the video and its player.

The [video and captions](https://github.com/hbinduni/ottodot-trial-booking/releases/tag/walkthrough-v1) are public GitHub Release assets. The [transcript](docs/narration.md) preserves the spoken wording.

## What could improve the process

Agreeing the payment rules and expected failure cases before building the interface would make review more focused. Reviewing the transaction, retry behavior, and a failing request with the candidate early would also help catch misunderstandings before UI work. Tests and a separate code review should remain part of that process. Any personal reflection should describe what the candidate actually reviewed and learned.
