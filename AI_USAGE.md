# AI usage

## Tools and scope

OpenAI Codex in the desktop app assisted with reading the task, proposing the architecture, writing the Bun/Hono/SQLite backend and React UI, generating synthetic fixtures, tests, and documentation, and running verification. A separate Codex reviewer examined the backend, concurrency tests, and revised UI. An image-generation tool produced the two decorative class illustrations, which were encoded as WebP. Playwright was used to exercise the running browser; it is a verification tool, not a payment provider.

The candidate asked for a senior full-stack implementation and accepted the proposed confirmation-time allocation with explicit `refund_required` handling. Most implementation code was generated by Codex. It should not be described as independently handwritten by the candidate.

The candidate also requested a narrated video and explicitly selected a generated English voice. Codex automated the browser recording against a separate synthetic database, prepared source-code and test-output excerpts, and assembled the video with FFmpeg. Narration uses the standard Microsoft Andrew Neural voice through `edge-tts`; captions follow speech-service timestamps. The opening and chapter headers disclose generated narration. This is not a recording of the candidate speaking. The [narration transcript](docs/narration.md) is available for review.

## Where AI accelerated the work

Codex quickly turned the last-seat requirement into executable database tests, including a synchronized test with eight independent processes and separate database connections. That provided concrete evidence about capacity and idempotency while keeping setup limited to Bun and a local SQLite file.

## Corrections during the AI-assisted session

The agent's first invalid-input test table used a bare empty array as a case. Bun treated it as an argument list, so the test sent no body instead of JSON `[]`. Inspection showed the error was in the fixture, not the JSON validator. Each case was wrapped in `{ body }`, and the test then verified the intended invalid-array behavior.

The reviewer also flagged imprecise design wording about payment replay. The documentation now distinguishes the original payment attempt from the current booking status, matching the implementation and its regression test.

The candidate then asked for a UI that felt like a more proper app. In response, Codex replaced the initial single-page demo layout with separate discovery, booking-history, and teacher-roster views, added filters and a booking dialog, and verified that the existing recovery and last-seat behavior still worked. This product direction came from the candidate; the resulting implementation was AI-assisted.

The UI reviewer found a stale-count inconsistency: a cached class selector could show three confirmed learners while the newly fetched roster showed four. The selector now shows the fixed class capacity, and actual occupancy is displayed with the roster snapshot.

The test-fixture and replay-wording changes were **agent/reviewer corrections**. The UI direction was candidate feedback. The candidate should review these facts and express the requested first-person reflection in their own words before submission.

## Workflow improvement

A useful improvement would be to agree the payment boundary and a concise acceptance matrix at the start, then make the candidate review the transaction, retry contract, and one failure case before UI work. Keep generated process documents short to preserve the four-hour timebox. Use executable tests and a separate review to challenge AI output instead of treating a plausible explanation as proof.
